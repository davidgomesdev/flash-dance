# Connecting the Launchpad Mini MK3 to Home Assistant

Research checked against current official Home Assistant documentation on **2026-10-06**. This is a design note, not a tested integration. No Home Assistant instance or Launchpad was queried for this research.

## What the two sides offer

The Launchpad is a USB MIDI controller, so a process on a computer with access to its MIDI port must own the device. In this repository, `flash-dance` is that owner: `Launchpad::connect` supplies a receiver of `Event::Press` and `Event::Release`, and the API's `Grid` and `set_all` drive its LEDs. The 8×8 grid, top row, and right column can be mapped to Home Assistant entities, scenes, scripts, or pages. The apps and effects runner already treat the MIDI port as one session at a time. The bridge should use the public Rust API, never construct MIDI bytes itself, and should own the port for its whole session. [Repo guide](../AGENTS.md) · [API source](../api/src/lib.rs)

Home Assistant exposes three useful paths:

- **WebSocket** at `/api/websocket`: authenticate, fetch state snapshots, subscribe to `state_changed`, call actions with `call_service`, and optionally fire custom events. Commands have IDs and `result` responses; subscriptions send later `event` messages. [WebSocket API](https://developers.home-assistant.io/docs/api/websocket/)
- **REST** under `/api`: fetch states, call actions, and fire events using a bearer token. REST has no streaming state subscription, so live LED feedback would need polling or another channel. `POST /api/states/<entity_id>` changes Home Assistant's representation only; it does **not** operate a physical device. [REST API](https://developers.home-assistant.io/docs/api/rest/)
- **MQTT integration**: broker topics can carry messages to and from Home Assistant. MQTT discovery can register a device and its components; MQTT device triggers or event entities can represent momentary pad presses. This requires an MQTT broker and the Home Assistant MQTT integration. [MQTT integration](https://www.home-assistant.io/integrations/mqtt/) · [MQTT device triggers](https://www.home-assistant.io/integrations/device_trigger.mqtt/) · [MQTT event entities](https://www.home-assistant.io/integrations/event.mqtt/)

For direct API access, a user can create a **long-lived access token** on their Home Assistant profile page. Home Assistant documents a ten-year validity. Treat it as a secret, keep it out of source control and logs, and use HTTPS/WSS when the bridge connects across an untrusted network. REST uses `Authorization: Bearer <token>`; WebSocket sends an `auth` message with `access_token` after `auth_required`. MQTT instead uses the broker's configured authentication and TLS. [Authentication API](https://developers.home-assistant.io/docs/auth_api/) · [WebSocket authentication](https://developers.home-assistant.io/docs/api/websocket/#authentication-phase) · [MQTT broker security](https://www.home-assistant.io/integrations/mqtt/#securing-the-connection)

## Options

| Approach | How it works | Good fit | Main cost |
| --- | --- | --- | --- |
| **1. Rust WebSocket bridge** | New `apps/home_assistant` binary reads Launchpad presses, calls HA actions, and paints pads from HA state events. | A responsive, two-way controller without HA-side custom code. | New JSON/WebSocket dependencies and reconnect logic. |
| **2. Rust MQTT bridge** | Binary publishes pad events and consumes broker topics for LED state; discovery can expose it as a device in HA. | An installation that already uses MQTT, or one wanting HA device automations. | Broker setup, topic/discovery lifecycle, and a feedback path to the LEDs. |
| **3. Rust REST bridge** | Binary calls HA actions or fires events; polls states to refresh LEDs. | A small proof of concept or sparse feedback. | Polling load and delayed state feedback. |
| **4. HA custom integration plus Rust device bridge** | Python integration inside HA talks to a separate Rust process that owns USB MIDI. | Polished HA setup and device/entity model for wider distribution. | Two processes, a transport between them, HA integration maintenance and packaging. |

### 1. Direct WebSocket bridge — recommended first implementation

1. Add an unpublished `apps/home_assistant` crate using `flash-dance = { workspace = true }`. Configure the HA base URL, token, and a fixed mapping from Launchpad pads to allowed HA targets/actions. Keep device access in the Rust binary; no change to `api/` is needed for the initial design. A network transport and JSON parser are justified here even though the existing non-web crates minimize dependencies. [Repo guide](../AGENTS.md)
2. Open `ws://<ha-host>:8123/api/websocket` on a trusted local network, or `wss://…/api/websocket` with TLS. After `auth_required`, send `{"type":"auth","access_token":"…"}` and wait for `auth_ok`. Give each subsequent command its own integer ID and inspect `success` in each `result`. [WebSocket API](https://developers.home-assistant.io/docs/api/websocket/#server-states)
3. Subscribe to `state_changed` and fetch `get_states`. Filter incoming events to mapped entity IDs and build the initial display from the snapshot. Handle the subscription/snapshot gap by applying the latest event per entity after the snapshot, or subscribe first and buffer changes until the snapshot is installed. Repeat both steps after reconnect. Home Assistant supplies `new_state` and `old_state` in state-change events. [Event subscription](https://developers.home-assistant.io/docs/api/websocket/#subscribe-to-events) · [State snapshot](https://developers.home-assistant.io/docs/api/websocket/#fetching-states)
4. On `Event::Press`, send a configured `call_service` command, for example `{"id":24,"type":"call_service","domain":"light","service":"toggle","target":{"entity_id":"light.desk"}}`. Treat the command result as execution feedback; paint the actual device state from `state_changed`, since action completion does not guarantee the device ended in the requested state. `Event::Release` can be ignored initially or mapped to an explicit hold/release action. Avoid assuming all entity domains support `toggle`; make domain, action and target explicit in the mapping. [Calling actions](https://developers.home-assistant.io/docs/api/websocket/#calling-a-service-action)
5. Render mapped states through `Grid` (for example, on = color, off = dim, unavailable/unknown = distinct warning color), then send one batched `set_all` for each relevant change or at a modest capped frame rate. Use top/right buttons for pages and status. The MIDI `Clock::tick` waits on its event receiver, so network work should run on a worker thread and exchange compact messages with the device loop; network delays must not stall button reads or LED pacing. `set_all` has no backpressure, so never send frames in an unpaced tight loop. [Repo guide](../AGENTS.md)
6. On lost HA connection, indicate offline status, suppress or queue only deliberately safe actions, reconnect with backoff, then resubscribe and resync. On normal exit, let `Launchpad` drop so its LED, brightness, and programmer-mode cleanup runs. The web effects session also owns the port, so running it concurrently requires a single explicit session owner and handoff rather than opening a second MIDI connection. [Repo guide](../AGENTS.md)

For a user-configurable automation instead of a hard-coded action map, the bridge can send `fire_event` with a custom event such as `flash_dance_pad` and data like `{"pad":81,"edge":"press","velocity":96}`. A Home Assistant automation can use an event trigger and inspect its event data. That supports arbitrary HA behavior but adds automation setup and leaves LED feedback dependent on monitored entities. [WebSocket `fire_event`](https://developers.home-assistant.io/docs/api/websocket/#fire-an-event) · [Automation event triggers](https://www.home-assistant.io/docs/automation/trigger/#event-trigger)

### 2. MQTT bridge with Home Assistant device discovery

1. Set up an MQTT broker and Home Assistant's MQTT integration. The Rust binary connects to the broker with its own credentials and owns the Launchpad. Choose a stable device identifier and topic prefix, such as `flash_dance/<device_id>/...`. [MQTT setup](https://www.home-assistant.io/integrations/mqtt/#setting-up-a-broker)
2. For each pad meant to trigger automations, publish MQTT device-trigger discovery on `homeassistant/device_automation/<device_id>/<pad_action>/config`, with `automation_type: "trigger"`, a stable `type`/`subtype`, `topic`, matching `payload`, and `device.identifiers`. Device triggers are discovery-only and are explicitly recommended over binary sensors for remote-control buttons. Alternatively create one or more MQTT event entities: publish JSON such as `{"event_type":"press","pad":81,"velocity":96}` on their `state_topic`, configure `event_types`, and do **not** retain press messages. The event entity represents a momentary occurrence, while a binary sensor represents an ongoing on/off condition. [Device-trigger configuration](https://www.home-assistant.io/integrations/device_trigger.mqtt/#configuration) · [MQTT event configuration](https://www.home-assistant.io/integrations/event.mqtt/#configuration) · [Event entity model](https://developers.home-assistant.io/docs/core/entity/event/)
3. For LED feedback, choose a specific contract. One route is HA automations that publish desired pad colors to `flash_dance/<device_id>/leds` when relevant entity states change, plus an initialization automation or retained desired-state messages. Another route is [MQTT Statestream](https://www.home-assistant.io/integrations/mqtt_statestream/) filtered to mapped entities, with the Rust bridge subscribing to their state topics. Statestream emits state changes; plan an initial snapshot or retained-state strategy instead of assuming it supplies a complete current view after restart. The bridge remains the only code that translates these messages into `Grid` and LED writes. [MQTT Statestream](https://www.home-assistant.io/integrations/mqtt_statestream/) · [Automation MQTT trigger](https://www.home-assistant.io/docs/automation/trigger/#mqtt-trigger)
4. Publish retained discovery configuration and a retained online/offline availability topic with an MQTT Last Will. Home Assistant's MQTT birth topic is `homeassistant/status` by default; rediscover after its `online` message if configuration is not retained. Do not retain button presses or other one-shot events. Home Assistant notes that discovered devices are unavailable until discovery is processed after MQTT starts. [Discovery lifecycle](https://www.home-assistant.io/integrations/mqtt/#birth-and-last-will-messages) · [MQTT discovery](https://www.home-assistant.io/integrations/mqtt/#mqtt-discovery)

MQTT can make the Launchpad appear as a Home Assistant device with usable automation triggers. The direct WebSocket bridge is simpler when the goal is only to control existing HA entities and mirror their state, because it needs no broker or separate feedback publication rules.

### 3. REST bridge for a narrow prototype

1. Use `GET /api/states/<entity_id>` at startup and periodically for mapped entities, authenticating with a bearer token. [REST states](https://developers.home-assistant.io/docs/api/rest/#get-api-states-entity_id)
2. On a press, `POST /api/services/<domain>/<service>` with the target entity, or `POST /api/events/flash_dance_pad` and define an HA event-triggered automation. Do not use `POST /api/states/<entity_id>` to control a device; official docs say it changes only HA's state representation. [REST actions and events](https://developers.home-assistant.io/docs/api/rest/#post-api-services-domain-service) · [REST state warning](https://developers.home-assistant.io/docs/api/rest/#post-api-states-entity_id)
3. Poll at a deliberately bounded interval and coalesce redraws. This works for a small set of lights, but fast external state changes will appear on the grid only after the next poll. WebSocket is the natural upgrade for live feedback. [REST API](https://developers.home-assistant.io/docs/api/rest/) · [WebSocket API](https://developers.home-assistant.io/docs/api/websocket/)

### 4. Home Assistant custom integration and Rust sidecar

1. Keep Rust as the USB MIDI process; expose a small local, authenticated IPC/WebSocket interface carrying pad events and LED commands. A Python custom integration under `<config_dir>/custom_components/flash_dance` connects to that process. HA's documentation places custom integrations there and requires a `version` in their `manifest.json`. [Creating an integration](https://developers.home-assistant.io/docs/creating_component_index/) · [Manifest](https://developers.home-assistant.io/docs/creating_integration_manifest/)
2. In the Python integration, register the Launchpad as a device; expose pads as event entities (with `PRESS_START`/`PRESS_END` where useful) or device automation triggers, and expose configurable commands for setting pages/colors. The event entity API says integrations call `_trigger_event` and then write the HA state; callbacks must be unregistered when removed. [Event entity developer API](https://developers.home-assistant.io/docs/core/entity/event/)
3. Add a config flow for sidecar address, mapping, and credentials, and define disconnect/reconnect and ownership behavior. This offers the most native HA user experience, but it does not eliminate the separate Rust process or the USB access requirement. It is justified after the interaction model is proven with one of the simpler bridges. [Integration architecture](https://developers.home-assistant.io/docs/creating_component_index/)

## Suggested first slice

Build option 1 with one page of eight mapped lights and one status pad. Read `get_states`, subscribe to `state_changed`, toggle a light on press, and update its pad only from the resulting state. Define the mapping in local configuration rather than encoding it in `api/` or in the web page. Test JSON/protocol handling with recorded or synthetic HA messages and a fake transport; then verify latency, reconnection, and LED colors against a real HA installation and the hardware when one is available. The research here intentionally did neither.
